## C. The horizon is a live axis, and the report's test for it is biased (HIGH)

TREASURE BEACH mirror, exact search, 250k nodes:
    maxTurns 24 -> undecided, 250,001 nodes, 12s, blockedByHorizon=FALSE
    maxTurns 40 -> FOUND 38T in 5,990 nodes, <1s      (42x fewer nodes)
    maxTurns 80 -> FOUND 38T in 5,990 nodes

Too SHORT a horizon costs MORE nodes: with no solution inside 24 turns the DFS
thrashes the whole budget in a solution-free space.

The report separates "budget-bound" from "horizon-bound" via blockedByHorizon,
which requires a full-width pass to FINISH its tree. A too-short horizon never
finishes -- it exhausts budget -- so it is classified budget-bound. **The test
cannot detect the condition it is used to rule out.**

The upward extension is gated on `!limits.exhausted && blockedByHorizon`, so it
can never fire on any fight big enough to matter. Verified:
    maxTurns 24 + maxTurnsCeiling 40 (what the app asks) -> undecided 250,001n
    maxTurns 24 + maxTurnsCeiling 60                     -> undecided 250,001n
Same "cap that is not a cap" shape as the beam-of-8.

NOT monotone, so it is a portfolio axis not a new constant:
    BROCK 4v4 mirror (60k): 24 -> FOUND 13T | 40 -> undecided | 60 -> FOUND 60T
    MISTY generated team (400k/60s): undecided at 24, 40 AND 60 -- unmoved.
Prevalence across all 139 NOT established (sweep would need ~6h; stopped).

## D. Root-dealing: same budget, partitioned by opening (HIGH on 1 fight)

## I. The restart ladder (the actual proposal) - first result

Iterative broadening: every opening gets an equal slice; if all fail, double the
slice and go round again. Removes root-dealing's regression mode (an opening
that is RIGHT but needs more than budget/N still gets there one doubling later).

    GYM LEADER BROCK 4v4   plain FOUND 13T / 26,296 nodes
                           ladder FOUND 14T /  8,944 nodes   (3x fewer, same cap)

No regression on a fight the plain search already solves; slightly longer line.

## J. Architectural reading

DFS's only advantage over best-first here is completeness, i.e. the right to say
"no clean line exists". That verdict fires in 3 of 139 mirrors (2%), and STATE.md
notes it is unreachable by construction on any fight longer than the horizon.
Its cost is the 17% (23/139) that come back undecided because depth-first spends
the whole budget under its first root branch.
=> the primary search wants restarts/best-first; exhaustive DFS should be a
separate mode for small fights where "no clean line" is actually answerable.

### The general caution this earns

A MIRROR IS SYSTEMATICALLY EASIER IN A WAY THAT MATTERS FOR MECHANISM CHOICE.
Both sides have the same team, so a clean line usually exists and is often
shallow enough for a greedy rollout to stumble into. Real fights fail for the
opposite reason: no easy clean line exists at all. So a mechanism measured as
valuable on mirrors may be worth zero in play, and the mirror benchmark cannot
tell you which.

This applies to MY OWN root-dealing result, which was also measured on a mirror
(BROCK 6v6). Transfer test running: ladder vs plain on generated teams vs real
trainers, the bench_hunt fights.

## O. THE CONCEPTUAL FRAME (the part worth keeping)

What this project has been fighting is a textbook **heavy-tailed runtime
distribution** in backtracking search (Gomes, Selman, Kautz). Backtrack-search
runtimes on combinatorial problems decay polynomially rather than exponentially:
most runs are short, a few are astronomically long, and the mean is dominated by
the tail. BROCK 6v6 (74 nodes down one opening, >250,000 down another) and
KINDLE ROAD (11 nodes vs 100,001) are textbook instances.

The literature's remedy is exactly what was measured here: **rapid randomized
restarts**, reported to give speedups "up to two orders of magnitude" on SAT and
CSP. Measured here: ~10x median, 1,193x best. Restarts require successive runs
to explore DIFFERENT parts of the tree; this project has a natural deterministic
diversifier (the root action set), so no randomness is needed.

**Luby's universal schedule** (1,1,2,1,1,2,4,1,1,2,4,8,... scaled by a unit) is
provably within a constant factor of the optimal fixed cutoff for ANY unknown
runtime distribution. The ladder tested here used naive doubling; Luby is the
principled schedule and is exactly what the CLAIR regression calls for.

### The reframe this gives the whole project

The portfolio, the fractional beam, the parallel root split and root-dealing are
ALL restart strategies. The project independently rediscovered four of them and
never named the principle -- which is why each arrived as a surprise and why
"which method is better" felt unanswerable. Naming it makes the next move
principled rather than empirical.

### If restarts saturate, the principled next step is NOVELTY

The diagnosis "the tree is wide and the transposition table has nothing to do
because HP drifts every turn" is precisely what **width-based search** solves
(Lipovetzky & Geffner's Iterated Width; Best-First Width Search is state of the
art for satisficing planning). Novelty asks not "have I seen this exact state"
but "does this state contain a small feature-tuple I have never seen" -- the
principled version of the `hpBuckets` hack already measured as worth 19%.
Features here: active mon each side, HP band, status, stat stages, hazards.

Sources: Gomes/Selman/Kautz heavy-tailed phenomena
https://www.cs.cornell.edu/gomes/pdf/2000_gomes_jar_phenomena.pdf ;
Luby restart strategies https://cs.uwaterloo.ca/~vanbeek/Publications/wu.pdf ;
width-based planning https://arxiv.org/pdf/2101.06177

# WHAT HAPPENED NEXT: the review's predictions, checked against implementation

Written after Phases 0a, 0b, 1 and 3 landed the same night. This section exists
because a review is a set of predictions, and most of the value is in which ones
survived contact.

## Held up

**Restarts were the lever.** Predicted from ~40 real fights (median 9.5x fewer
nodes, best 1,193x). Shipped and measured across all 139 mirrors: clean wins
113 -> 125, undecided 23 -> 11, and the count of fights PROVED to have no clean
line did not move, which is exactly what should happen -- restarts change when
an opening is searched, never which lines exist.

**The Elite Four was compute, not capability.** It looked structural. Agatha now
returns in 520 nodes and Bruno in 156, both previously undecided at 250,000.

**Three of the five mirror "losses" were reporting artifacts.** Confirmed: at a
160-turn cap the stalls become wins and the sweep reports 2 real losses, not 5,
with 0 stalls left.

**Min-loss was worth building but was never a five-fight problem.** One fight,
NELLE, and the planner now wins it losing 1 instead of losing 0-2. The predicted
risk -- that relaxing the Nuzlocke cut would explode the tree -- did not
materialise: 1,051 / 1,959 / 5,531 nodes at k=0/1/2.

**The horizon was ruled out by a test that could not detect it.** Confirmed, and
the fix needed a second correction of its own: gating a deeper rung on an
opening FINISHING truncated never fires either, because openings run out of
cutoff long before they run out of tree. What earns a deeper look is simply
having seen lines run past the horizon.

## Did not hold up, or needed correcting

**"Restarts are the general form of the beam and the portfolio, so they can
replace them."** WRONG, and measured wrong within the hour. Dropping the beam
for restarts cost Lt. Surge, whose line the beam finds in 7,423 nodes and which
full-width restarts do not reach. They hedge against different failures -- a
beam gets DEEP fast, a restart stops one opening swallowing everything. Restarts
were added to the portfolio, not substituted into it. This is the third time
this project has found that no single search trick dominates.

**A false regression alarm, from benchmarking against the docs.** bench_hunt
appeared to show Lt. Surge regressing from a documented 22,585-node witness to
undecided. It had not: the generator's fingerprint moved when restricted-mode
filtering landed, so TUNING's numbers describe teams the generator no longer
produces. The baseline for a change is the same code with the change switched
off, and nothing else.

## What the review MISSED entirely

**It measured the benchmark's settings and never the app's.** At the app's real
budget of 60,000,000 nodes, both the new restart unit (833,000) and the existing
hunt-pass shares (3M and 12M) became so large that the driver was never reached.
Brock came back undecided at the app's own settings while solving fine at
250,000. The whole change would have shipped as a silent no-op in the only
caller that matters.

That is the third instance in this repo of a limit that stops limiting when the
thing it limits gets big -- after the beam of 8 that never narrowed a 4v4 and
the horizon extension that cannot fire on a budget-bound fight. **It should have
been the first thing checked, and it is now a standing question: what does this
do at the budget the app actually passes?**

**A fourth private copy of shared logic.** `planRoute` carried its own copy of
`fallbackRoute`'s tail, so the min-loss wiring worked in the parallel search path
and did nothing in the page. The review catalogued three such copies as history;
it did not think to look for more.
